# M2 Benchmark Results

## Method

| | |
|---|---|
| Machine | Apple M3, macOS 26.5.1 |
| Python | 3.12.13 (CPython) |
| C++ build | Apple clang 21, CMake `Release` (`-O3`), C++17 |
| Workload | `bench/orderflow.py`, seed 42, N = 1,000,000 ops: 60% limit, 30% cancel, 10% market. Every cancel targets an order that is still resting (0 of 299,446 cancels are rejected). |
| Warm-up | The first 10% of the ops run on a throwaway book and are discarded. This mostly warms Python's code paths and allocator; there is no JIT on either side. |
| Runs | 5, each on a fresh book. Every number below is the **median** of the 5. |
| Timing | `python` and `cpp`: `time.perf_counter_ns()` around every call, including the harness's `apply()` dispatch (tens of ns). `cpp-raw`: `std::chrono::steady_clock` around the whole loop, inside C++. |
| Reproduce | `uv run python bench/run.py --impl {python,cpp,cpp-raw}` |
| M1 row | Run on a checkout of commit `7af7e4a` (M1 engine plus the harness), with the current `bench/` files copied in, so it uses the same workload. |

Raw results:
- JSON: `m2-baseline.json` (the M1 engine), `m2-python.json`, `m2-cpp.json`, `m2-cpp-raw.json`
- Deep-cancel results: `m2-deep-cancel.jsonl`
- cProfile output: `m2-profile-before.txt`, `m2-profile-after.txt`

## Main workload

| Engine | Throughput (ops/sec) | vs M1 | limit p50 / p99 ns | cancel p50 / p99 ns | market p50 / p99 ns |
|---|---:|---:|---:|---:|---:|
| Python, M1 (baseline) | 793,488 | 1.0× | 1,000 / 3,583 | 500 / 1,000 | 3,125 / 7,584 |
| Python, M2 optimized | 776,347 | 0.98× | 1,000 / 3,791 | 541 / 1,000 | 3,333 / 8,000 |
| C++ called per op from Python (`FastOrderBook`) | 1,321,189 | 1.67× | 541 / 2,208 | 542 / 666 | 2,125 / 4,583 |
| C++ raw, whole op list inside C++ (`run_ops`) | 16,227,378 | **20.5×** | 61.6 ns/op mean (no percentiles) | | |

Repeated runs of the same engine vary by about ±5%. So "Python M2 optimized" is the
**same speed as M1 on this workload**.

## Deep price level: cancel cost

`bench/deep_cancel.py` puts K orders on one price, then cancels them all in random order.

| Engine | K = 1,000 | K = 20,000 |
|---|---:|---:|
| Python, M1 (`deque` per level) | 1,784 ns/cancel | 29,293 ns/cancel |
| Python, M2 (`OrderedDict` per level) | 373 ns/cancel | 387 ns/cancel |
| C++ per op from Python | 388 ns/cancel | 396 ns/cancel |

The M1 cancel is O(k), so it grows with the queue. The M2 cancel is O(1), so it stays
flat: about **76× faster at K = 20,000**.

## What the numbers say

1. **The Python optimization fixed the complexity, not the constant.** The profile
   showed time going to the matching loop, the sorted-dict lookup and per-call object
   work. Levels in this workload are shallow, so an O(k) cancel was already cheap. Making
   cancel O(1) only pays off when levels are deep, which the deep-level test shows
   clearly. On the main workload it makes no difference.
2. **Most of a per-op call into C++ is overhead.** Each `FastOrderBook` call costs about
   757 ns end to end (1 / 1.32M ops/sec), but only 61.6 ns of that is the engine. So
   about **92% of each call is the Python↔C++ boundary plus the harness**:
   - argument conversion
   - building the result tuples and turning them into Python dataclasses
   - the harness's own dispatch and timer calls

   For cancel, which does very little engine work, the C++ path's median is no better
   than pure Python's (542 vs 541 ns). Its p99 is better (666 vs 1,000 ns).
3. **To get the C++ speed, stay in C++.** Batching, as `run_ops` does, is how real
   systems avoid paying the boundary on every message. The M4 backtester should replay
   market data in batches for the same reason.
