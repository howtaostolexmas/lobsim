# M2 Benchmark Results

## Method

| | |
|---|---|
| Machine | Apple M3, macOS 26.5.1 |
| Python | 3.12.13 (CPython) |
| C++ build | Apple clang 21, `-O3` via CMake `Release`, C++17 |
| Workload | `bench/orderflow.py`, seed 42, N = 1,000,000 ops (60% limit, 30% cancel, 10% market) |
| Warm-up | first 10% of the ops on a throwaway book, discarded |
| Runs | 5, each on a fresh book; every number below is the **median** of the 5 |
| Timing | `python`/`cpp`: `time.perf_counter_ns()` around every call (adds tens of ns per op). `cpp-raw`: `std::chrono::steady_clock` around the whole loop inside C++ |
| Reproduce | `uv run python bench/run.py --impl {python,cpp,cpp-raw}` |

Raw JSON: `m2-baseline.json` (the M1 engine), `m2-python.json`, `m2-cpp.json`, `m2-cpp-raw.json`.
cProfile output: `m2-profile-before.txt`, `m2-profile-after.txt`.

## Main workload

| Engine | Throughput (ops/sec) | vs M1 | limit p50 / p99 ns | cancel p50 / p99 ns | market p50 / p99 ns |
|---|---:|---:|---:|---:|---:|
| Python, M1 (baseline) | 762,721 | 1.0× | 1,000 / 4,125 | 375 / 1,125 | 3,125 / 7,292 |
| Python, M2 optimized | 706,098 | 0.93× | 1,042 / 4,667 | 375 / 1,042 | 3,417 / 8,375 |
| C++ called per op from Python (`FastOrderBook`) | 1,109,715 | 1.45× | 542 / 2,750 | 542 / 791 | 2,166 / 4,542 |
| C++ raw, whole op list inside C++ (`run_ops`) | 16,264,526 | **21.3×** | 61.5 ns/op mean (no percentiles) | | |

Repeated runs of the same engine vary by about ±5%. So "Python M2 optimized" is
**no faster than M1 on this workload**: the 0.93× is at the edge of that noise.

## Deep price level: cancel cost

`bench/deep_cancel.py` places K orders on one price and cancels them in random order.

| Engine | K = 1,000 | K = 20,000 |
|---|---:|---:|
| Python, M1 (`deque` per level) | 1,771 ns/cancel | 30,138 ns/cancel |
| Python, M2 (`OrderedDict` per level) | 386 ns/cancel | 379 ns/cancel |
| C++ per op from Python | 498 ns/cancel | 422 ns/cancel |

The M1 cancel is O(k) and grows with the queue. The M2 cancel is O(1) and stays flat:
about **80× faster at K = 20,000**.

## What the numbers say

1. **The Python optimization fixed the complexity, not the constant.** The profile
   showed that time goes to the matching loop, the sorted-dict lookup and per-call
   object work. Cancel was not hot, because levels in this workload are shallow. Making
   cancel O(1) only pays off when a level is deep, and the deep-level test shows that
   clearly. On the main workload it is a wash.
2. **The Python↔C++ boundary costs most of the time.** Per op, `FastOrderBook` takes
   about 900 ns (1 / 1.11M ops/sec), while the engine itself takes 61.5 ns. So roughly
   **93% of each per-op call goes to crossing the boundary**: argument conversion,
   building result tuples, and turning tuples into Python dataclasses. For cancel, the
   C++ path is even *slower* than pure Python (542 vs 375 ns p50), because there is so
   little engine work to amortize that cost.
3. **To get the C++ speed, stay in C++.** Batching, as `run_ops` does, is how real
   systems avoid paying the boundary on every message. The M4 backtester should replay
   market data in batches for the same reason.
